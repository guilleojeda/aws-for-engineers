If you used Amazon RDS Performance Insights to investigate a slow database, the monitoring experience has moved. AWS ended the Performance Insights console experience on July 31, 2026, and migrated its users to CloudWatch Database Insights. The Performance Insights API remains available. This guide explains how to use Database Insights to find what is driving database load, read the signals correctly, and choose a safe next step.

The most useful starting point is the database load chart. It breaks active sessions down by wait event, SQL statement, host, or user. Pair that view with CloudWatch resource metrics and application latency: Database Insights helps explain database activity, while those other signals help show whether the issue is CPU capacity, storage, a lock, a workload change, or something upstream.

What changed from Performance Insights?

Performance Insights' former RDS console dashboard is no longer the supported console experience. The old entry point redirects users to CloudWatch Database Insights. Existing RDS monitoring configuration and the Performance Insights API continue to use names such as EnablePerformanceInsights; their presence in an API request or infrastructure template does not mean the retired console is still in use. See the current CloudWatch Database Insights overview and the Performance Insights API reference for the current product and API details.

Database Insights is the monitoring experience for Amazon RDS and Amazon Aurora. It has Standard and Advanced modes with different capabilities. Support and configuration details depend on the database engine, Region, and instance class, so check the current AWS support page for the database you run before changing its settings.

Before you use Database Insights

Check engine, Region, and instance support

Database Insights covers Amazon RDS for MariaDB, MySQL, PostgreSQL, Oracle, and SQL Server, as well as supported Amazon Aurora databases. Exact engine versions, Regions, and instance classes vary. Use the current Amazon RDS Database Insights support matrix and the separate Aurora matrix instead of relying on a copied list of versions or small-instance exclusions.

This article focuses on managed RDS and Aurora databases. Database Insights also has a separate setup for self-managed PostgreSQL on EC2; its modes and configuration are different.

Enable the appropriate Database Insights mode

For an RDS instance or Multi-AZ DB cluster, select Database Insights when creating or modifying the database. Standard mode provides the core DB load and top-contributor views. Advanced mode adds capabilities such as fleet views, detailed per-query statistics, selected execution-plan and lock analysis, and process-level operating-system views when their prerequisites are met. The supported features differ by engine and Region.

When a workflow or template still refers to Performance Insights, consult the current RDS instructions for the corresponding Database Insights setting. Do not assume that an older console walkthrough still matches today's labels or available choices.

Grant access to the data people need

Database Insights uses permissions across CloudWatch and RDS; features that display logs also depend on CloudWatch Logs access. Use the current AWS Database Insights permissions guidance to scope access for your account and enabled features. SQL text and workload dimensions can reveal sensitive application or customer details, so limit dashboard and query-text access to the people who need it.

Turn on and configure Database Insights

When creating a database

  1. In the Amazon RDS console, start creating a supported DB instance or Multi-AZ DB cluster.
  2. In the Database Insights settings, choose Standard or Advanced if both are available for that engine and Region.
  3. Review the retention choice, encryption key, and any feature-specific requirements shown for the database.
  4. Create the database, then open its view in the CloudWatch Database Insights console to confirm that load data is appearing.

Console choices can vary by database type. Follow the linked AWS procedure for the engine you are creating rather than treating these steps as a universal list of settings.

When modifying an existing database

Choose the DB instance or cluster in the RDS console, select Modify, and review the Database Insights section. Pick the mode and retention appropriate for the workload, then apply the change using the options AWS presents. For a cluster, check whether monitoring settings are managed at the cluster level; do not try to change a setting independently on an instance when the cluster owns it.

For API or infrastructure-as-code changes, use the current engine-specific RDS documentation. AWS still uses Performance Insights API parameter names for some Database Insights settings, and Advanced mode requirements can differ between service-level summaries and engine-specific procedures.

Understand modes, retention, and cost

The current CloudWatch Database Insights overview describes these retention options:

  • Standard mode: up to 7 days of detailed database and per-query metrics at no additional charge; retention from 1 to 24 months is paid at the same price as Performance Insights.
  • Advanced mode: this is paid monitoring, with 1 to 24 months of detailed database and per-query metrics retention included in the mode's price.

These statements describe retention for those metrics; they do not mean that the database, CloudWatch, logs, or every Advanced feature has no cost. Check the current CloudWatch pricing page for charges tied to your configuration and Region.

AWS documentation is not fully aligned: the CloudWatch mode overview lists flexible 1–24 month retention for Advanced mode, while the current RDS Advanced-mode setup procedure still specifies a 15-month minimum (465 days) for enabling it. Do not copy a fixed retention value from an older CLI example. Check the current console or engine-specific procedure for the exact database you are changing, and confirm the applicable cost before applying the change.

Read the Database Insights dashboard

Fleet and database views

Database Insights offers a fleet view for finding databases that need attention and an instance view for investigating one database. The instance view brings the database load chart and related metrics together. Select a DB instance, choose the time range that matches the reported symptom, then compare the same interval with application latency, request volume, database events, and CloudWatch metrics.

What the load chart shows

Database load, or DBLoad, is measured as average active sessions (AAS). An active session has submitted work and is either running on the CPU or waiting for a resource. AAS is therefore a measure of concurrent database activity, not a CPU percentage and not a count of every open connection.

The chart can divide load by dimensions such as waits and SQL. A maximum-vCPU line gives a reference for the instance's CPU capacity. Read that line together with the wait breakdown: load above the line with CPU as the main load component can indicate CPU pressure, while load dominated by storage or lock waits points to a different investigation.

Use top contributors to narrow the search

The Top SQL view ranks statement patterns by their contribution to DB load and shows related statistics. It helps distinguish a widely used query pattern from an isolated slow request. A high ranking identifies where to investigate; it does not prove that the SQL itself is defective. Compare the statement's load, call rate, and timing with the period when the application slowed down.

Analyze database load

Interpret average active sessions

AAS is the average number of sessions actively doing database work during an interval. If AAS rises with application traffic, the database may simply be serving more work. If latency rises while traffic is steady, inspect which waits and SQL statements make up the increase. Idle connections do not count as active sessions just because they are open.

Compare DB load with the maximum-vCPU reference and the database's CloudWatch CPUUtilization metric. AAS can be high because sessions are waiting; it does not by itself establish CPU saturation. The AWS database load guide explains AAS, active sessions, waits, and dimensions.

Find the dominant constraint

Start with the largest DB load contributors, then check the matching resource signals and database context:

  • CPU activity: compare DB load, CPU utilization, and the top SQL statements. Heavy CPU load may call for query tuning, connection control, or a capacity change, depending on workload and instance headroom.
  • Storage or I/O waits: compare read and write latency, throughput, queue depth, and the statements driving reads or writes. Confirm the relevant storage and engine limits before changing storage.
  • Lock waits: inspect the transactions and statements involved, their duration, and whether a long-running transaction is blocking others. Lock diagnosis is available only for supported engines and modes.
  • Other engine-specific waits: use the database engine's wait-event documentation and inspect the corresponding counter or log. A wait name is a clue about where a session stopped, not a complete root-cause diagnosis.

Use the evidence to form a hypothesis, then validate it against the application symptom and a comparable workload period before changing instance size, indexing, query shape, or connection behavior.

Slice load by waits, SQL, host, and user

Each dimension answers a different question. The wait breakdown separates CPU activity from sessions waiting on I/O, locks, or other engine resources. SQL points to the statement patterns contributing to load. Host and user can help identify where or under which database identity the work runs. Use these dimensions together: for example, a storage wait concentrated in one SQL pattern is more actionable than a database-wide I/O counter alone.

Availability of dimensions and detail differs by engine. Keep in mind that a host or database user is not necessarily the same thing as an application service, and the dashboard cannot infer application ownership when the database does not expose that association.

Combine database load with resource metrics

Separate database and operating-system signals

Database Insights' DB load and wait events describe database sessions. Amazon CloudWatch's RDS metrics describe other signals, such as CPU utilization, freeable memory, connections, storage throughput, and latency. Enhanced Monitoring exposes operating-system-level metrics; Advanced Database Insights can show detailed processes when RDS Enhanced Monitoring is enabled. These signals answer related but different questions, so do not label an OS metric as a database wait or treat every counter as query attribution.

Choose metrics that fit the symptom

For an apparent CPU issue, compare CPU utilization with DB load and the CPU portion of DB load. For an I/O issue, examine the relevant read/write latency and throughput metrics along with I/O waits. For connection pressure, look at connection counts and the sessions consuming load. The metric set and names vary by engine; compare a useful baseline and the affected interval instead of relying on a single universal threshold.

Investigate SQL statements and plans

Read statement patterns and statistics

Top SQL commonly groups statements with the same parameterized shape into a digest. This reduces noise from queries that differ only in literal values. Use the digest to locate a costly pattern, then inspect its call volume and available query-level statistics. The exact statistics depend on the database engine and mode.

Prioritize SQL that explains the incident

  1. Choose the time range when user-facing latency or errors increased.
  2. Rank Top SQL by contribution to DB load, and compare the leading statements with the normal period.
  3. Check whether a statement became more frequent, more expensive per call, or both.
  4. Inspect the query and related database metrics before changing indexes, query structure, or application behavior.

High total load and high latency per call are different signals. A fast query called extremely often can dominate load; a slow query called rarely may have little effect on the overall database.

Use execution plans when supported

Execution plans show how the database engine intends to access and combine data. Database Insights plan capture and guided analysis require Advanced mode and are available only for selected engines. Check the current feature matrix for your engine before expecting plans in the console. Review a plan with the query's statistics and schema; a scan or join is not automatically a defect without workload context.

Use CloudWatch for context and alerting

Know what is already available

Database Insights is a CloudWatch experience, and supported RDS metrics are available in CloudWatch for graphs and alarms. Advanced mode can also import Performance Insights counter metrics into CloudWatch automatically. You do not need to build a Lambda function that copies every metric through the API just to use the built-in database views. The Performance Insights API remains available for custom integrations or workflows that need it.

Build alerts around a symptom

Choose a metric or alarm condition that corresponds to a user-visible problem or a confirmed capacity risk. Combine a DB load signal with a resource or application metric when that reduces false alarms, and set periods and evaluation rules from observed workload behavior. Avoid paging on a short, harmless spike. See the related guide to CloudWatch alarm thresholds and conditions for practical alarm design.

Correlate the full request path

CloudWatch metrics and logs add resource and event context; application tracing or service telemetry can show which upstream request generated work. Use these together with database waits and SQL to distinguish a database bottleneck from a traffic surge or application behavior. Slow SQL visibility in Database Insights requires database log export to CloudWatch Logs and the engine-specific configuration described in the AWS guide.

A practical troubleshooting workflow

Start with one incident window

  • Record the symptom, affected database, and time window from the application or alert.
  • Compare that interval with a normal period at similar traffic levels.
  • Use DB load, wait events, and Top SQL to identify the largest change.
  • Check matching CloudWatch metrics, events, and logs before deciding on a cause.
  • After a change, compare the same signals under a representative workload and confirm application latency improved.

Tune the cause, not just the largest number

If SQL contributes most of the load, inspect query frequency, plans, indexes, and the application call pattern. If waits are caused by storage, locks, or a constrained instance, check those resources and their limits. Make one well-scoped change at a time where practical and measure the result. For broader RDS tuning strategies, see the RDS performance tuning guide.

Know what the dashboard cannot prove

Database Insights samples database activity and presents selected metrics. It does not, on its own, prove that a specific SQL statement caused application latency, that a CPU spike requires a larger class, or that every query pattern is unhealthy. Confirm the timing and impact with application metrics, resource headroom, database logs, and a repeatable test when the proposed change carries operational risk.

Strengths and limits

Database Insights is useful when you need a managed view of RDS/Aurora load, waits, and leading SQL contributors. Its value depends on the engine, Region, mode, retention, and configured log or monitoring prerequisites. CloudWatch resource metrics and Enhanced Monitoring add different context; database-native tools and application tracing may still be needed for details those views do not collect.

Choose a next action from the evidence

Use a query-level finding to investigate SQL and its execution plan; use sustained CPU load plus high CPU utilization to evaluate compute capacity; use I/O waits with storage metrics to investigate storage or access patterns; and use lock waits to investigate transaction behavior. If the evidence points to persistent capacity mismatch, the RDS rightsizing guide covers how to compare resource demand before changing an instance class.

Conclusion

Key points

  • The Performance Insights console experience ended on July 31, 2026; CloudWatch Database Insights is the current dashboard for RDS and Aurora monitoring.
  • The Performance Insights API remains available, and some RDS configuration fields retain the older Performance Insights names.
  • DB load is AAS: active sessions running or waiting. It is not a CPU percentage or an open-connection count.
  • Read waits, Top SQL, CloudWatch resource metrics, logs, and application signals together before choosing a fix.
  • Retention and Advanced-mode setup guidance currently differs between the CloudWatch overview and some engine-specific RDS procedures. Verify the option and price for your database before applying changes.

For the current feature matrix and setup instructions, start with the CloudWatch Database Insights documentation and follow its engine-specific RDS or Aurora links.
